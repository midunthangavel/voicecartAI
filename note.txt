# 3) The biggest production upgrades you must make

## A. Replace the fragile state model

### Current problem

The current session model is in memory:

* lost on restart
* impossible to scale horizontally
* unsafe for multi-instance deployment

### Upgrade

Use:

* **Redis** for active session state
* **PostgreSQL** for durable session/order history
* **object storage** for audio recordings

### Result

You can restart servers, scale to multiple instances, and resume conversations safely.

---

## B. Introduce a real order state machine

### Current problem

Dialogue and order logic are too close together.

### Upgrade

Create a formal order lifecycle:

```text
new
→ collecting_items
→ collecting_address
→ pricing
→ awaiting_confirmation
→ confirmed
→ dispatched
→ completed
→ cancelled
→ failed
```

### Why this matters

This removes ambiguity and prevents AI from “jumping steps”.

### Implementation

Put the state machine in a dedicated service, not inside the dialogue prompt alone.

---

## C. Separate AI from business rules

### Current problem

The LLM is currently too central. That is risky.

### Upgrade

Use this split:

* **LLM**: natural language understanding, paraphrasing, intent extraction
* **Rules engine**: totals, validation, item lookup, ordering constraints, address validation, confirmation handling

### Why

The AI should suggest; the code should decide.

This is the single most important production design principle in your system.

---

## D. Queue all side effects

### Current problem

Payment links, WhatsApp messages, SMS, recordings, and ONDC calls should not be done inline with the voice request.

### Upgrade

Use a job queue:

* BullMQ / Redis
* or RabbitMQ / SQS

### Jobs to queue

* create payment link
* send WhatsApp receipt
* send SMS confirmation
* dispatch ONDC order
* persist recordings
* retry failed notifications

### Why

Voice systems need low latency. Side effects must not block the live call.

---

## E. Add authentication and tenant isolation

### Current problem

The dashboard and APIs appear open.

### Upgrade

You need:

* merchant login
* admin login
* role-based access control
* tenant scoping by merchant ID
* API keys for webhook sources
* Twilio signature verification

### Minimum roles

* `admin`
* `merchant_owner`
* `merchant_staff`
* `support`

### Why

Without tenant isolation, you cannot safely sell the product.

---

## F. Harden the webhook and media pipeline

### Current problem

Telephony pipelines are fragile by nature.

### Upgrade

Add:

* Twilio signature verification
* request size limits
* socket auth for media streams
* backpressure handling
* reconnect / resume strategy
* timeout handling
* circuit breakers for STT/TTS/LLM calls

### Why

A voice call that breaks mid-conversation destroys trust immediately.

---

## G. Replace SQLite with PostgreSQL for production

### Current problem

SQLite is fine for local MVP and demos, but not for serious production concurrency.

### Upgrade path

* Keep SQLite for local dev
* use PostgreSQL in production
* add migrations using Prisma, Drizzle, Knex, or plain SQL migrations

### Why

You need:

* concurrency
* scaling
* robust transactions
* better indexing
* stronger operational safety

---

## H. Add observability from day one

### Current problem

You have logs, but not a proper observability stack.

### Upgrade

Add:

* structured JSON logs
* request IDs
* call/session IDs
* OpenTelemetry traces
* metrics dashboard
* error monitoring

### Track these metrics

* call answer rate
* STT latency
* LLM latency
* TTS latency
* order conversion rate
* confirmation rate
* payment success rate
* WhatsApp delivery rate
* missed-call callback success rate
* average handling time
* abandonment rate

### Why

Without metrics, you cannot know what to fix or prove ROI.

## Core idea

A customer calls a phone number, and that call connects to your backend. The backend then:

* listens to the customer’s speech,
* understands the order,
* asks follow-up questions if needed,
* confirms the order,
* stores it in the database,
* and optionally triggers payment / WhatsApp / restaurant notification.

## In one line

**Voice call → backend → order capture → order confirmation**

So this is **not** a general app-first product. The **phone call is the primary user interface**.

That distinction matters because the production design should optimize for:

* low latency,
* call stability,
* accurate speech handling,
* robust conversation flow,
* and reliable order persistence.

Yes. For a **phone-call-to-order backend system**, the best improvements are not cosmetic. They are about **conversion, reliability, and merchant trust**.

## Highest-impact improvements

### 1) Make order capture deterministic

Do not let the AI “freestyle” the order flow.

Use a fixed flow:

* greet
* identify restaurant
* capture items
* capture quantity
* capture address / pickup details
* confirm subtotal
* final confirmation

This reduces hallucination and order mistakes.

### 2) Add a strict menu catalog

The backend should know:

* valid items
* variants
* add-ons
* out-of-stock items
* prices
* taxes
* minimum order rules

The AI should only map speech to this catalog.

### 3) Add confirmation checkpoints

For example:

* item summary
* total amount
* delivery address
* final “place order” confirmation

This is one of the most important production improvements.

### 4) Add human fallback

If the call becomes unclear, route to:

* restaurant staff
* support agent
* callback request

A real business needs an escape path.

### 5) Add call transcription and replay

Store:

* audio
* transcript
* extracted intent
* final order JSON

This helps debugging, audit, and training.

### 6) Add merchant dashboard

The merchant should see:

* live calls
* active orders
* failed calls
* cancelled orders
* payment status
* call history
* customer notes

This makes the product feel real and trustworthy.

### 7) Add analytics

Track:

* call answer rate
* order completion rate
* average call time
* abandonment point
* payment success rate
* failed intent parsing
* order correction rate

This tells you where the system breaks.

### 8) Add retries and failure recovery

If Twilio, STT, TTS, or LLM fails:

* retry once or twice
* fall back to simpler prompts
* save the session
* continue from last known step

### 9) Add multi-tenant support

Each restaurant must have:

* its own menu
* its own branding
* its own phone number or routing
* its own orders
* its own dashboard data

Without this, scaling becomes messy.

### 10) Add cost controls

Voice AI can get expensive quickly.

Put limits on:

* max call duration
* max LLM tokens
* max retries
* max STT/TTS usage
* provider fallback rules

## Best business improvements

### 11) Make ROI visible

### 12) Integrate WhatsApp order confirmation
